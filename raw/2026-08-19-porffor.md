# Porffor  *(poor-for)* /ˈpɔrfɔr/

An ahead-of-time JavaScript compiler

Repository: [github.com/CanadaHonk/porffor](https://github.com/CanadaHonk/porffor) · Homepage: [porffor.dev](https://porffor.dev) · MIT · ~5.0k stars (as of clip date) · Language: JavaScript · Created 2023-06-25

```sh
curl -fsSL https://porffor.dev/install.sh | sh
```

```
$ cat hello.js
console.log('hello world!');
$ porf hello.js -o hello
[105ms] compiled hello.js -> hello (33.7KB)
$ ./hello
hello world!
```

Porffor is a 100% AOT compiled JS engine/runtime. There is nothing interpreted or compiled just-in-time. Porffor compiles JS to C (with an IR inbetween). We chose this approach because:

- it can be used essentially everywhere
- is relatively easy to emit and compile
- it avoids directly depending on a backend like LLVM or Cranelift
- is easily modifiable post-compile for diverse environments

Official positioning (porffor.dev): **porffor rebuilds the JS engine as a compiler: an order of magnitude lighter in memory and binary size.**

Also described in docs as: a from-scratch experimental **AOT** optimizing JS/TS → Wasm/C engine/compiler/runtime in JS. Research project, not yet intended for serious use.

## Versioning

Porffor releases use a single increasing release number. Releases are automatically published every git push after CI testing.

Docs also describe a version scheme such as `0.61.10`:

1. **0** — Major version (always 0 until Porffor is production-ready)
2. **61** — Minor version (Test262 pass percentage, rounded half-down)
3. **10** — Micro version (build number for that minor version)

This means version `0.61.10` passes 61% of Test262 tests and is the 10th build at that pass rate.

## Official site claims (porffor.dev)

### Efficiency

Porffor is an order of magnitude more memory efficient than other runtimes. On a server with 1GB of memory, Porffor fits over 1 thousand applications under load. 40x Node containers and 25x self-hosted workerd.

| Runtime | Density | Memory / app |
|---------|---------|--------------|
| Node containers | 28 apps/GB | 37 MB/app |
| Self-hosted workerd | 45 apps/GB | 23 MB/app |
| Porffor processes | 1,144 apps/GB | 0.9 MB/app |

### Distribution

Porffor ships your program as a single file that users just run. With small apps over 50x smaller than bundling a runtime like Bun and Deno, as Porffor instead truly compiles ahead-of-time.

| Artifact | Size |
|----------|------|
| Porffor | 2.6 MB |
| Node | 137 MB |
| Deno | 79 MB |
| Bun | 59 MB |

### Conformance

Rebuilding the JS engine requires reimplementing the entire language from scratch. Porffor tests against Test262, the official ECMAScript conformance suite. Porffor is alpha and still has a lot of compatibility bugs, but it is improving every commit.

## What Makes Porffor Different

From the documentation introduction:

- No JIT compilation or interpreter. Your code is compiled ahead-of-time directly to WebAssembly or native binaries.
- No constant runtime or preluded code. The compiled output contains only what your code needs.
- Only essential I/O operations are imported. Everything else is compiled into your binary.
- Built entirely from the ground up (except the parser). Porffor generates final Wasm binaries itself without relying on tools like Binaryen.

Key differences (README-style summary):

- 100% AOT compiled (no JIT or interpreter)
- Zero constant runtime/preluded code
- Least Wasm imports possible (only I/O)

Porffor is a research project exploring new approaches to JavaScript compilation. While it has significant limitations, what it can do, it does exceptionally well.

## Architecture

Porffor is primarily built from scratch with minimal dependencies:

- **Parser**: Uses [Acorn](https://github.com/acornjs/acorn) (with support for Babel, Meriyah, and Hermes parsers)
- **Compiler**: Custom-built code generator that produces WebAssembly bytecode
- **Assembler**: Creates spec-compliant Wasm modules from scratch
- **2c**: Porffor's own WebAssembly-to-C compiler for native binary generation

Binaryen/etc is not used; final Wasm binaries are made by Porffor itself.

### Compilation Pipeline

```
JavaScript/TypeScript → Parser (Acorn) → AST → Code Generator
  → Wasm Bytecode → Optimizer → Assembler → Wasm Module
  → 2c Compiler → Native Binary
```

The parser (Acorn) is the only required external dependency. Everything else—from bytecode generation to final assembly—is built from scratch.

### Compilation Targets

- **WebAssembly** — Generate standalone `.wasm` files
- **C** — Compile to C code using Porffor's 2c compiler
- **Native Binaries** — Create executable binaries for your platform
- **REPL** — Interactive JavaScript execution
- **AWS Lambda** — Compile to Lambda deployment packages (`porf lambda`)

## Installation

Quick install (official site):

```sh
curl -fsSL https://porffor.dev/install.sh | sh
```

npm:

```bash
npm install -g porffor@latest
porf --version
```

Requires a modern Node.js.

From source:

```bash
git clone https://github.com/CanadaHonk/porffor.git
cd porffor
npm install
./porf path/to/script.js      # Unix
.\porf path/to/script.js      # Windows
```

The compiler itself can be run on Node.js, Deno, or Bun:

```bash
node runtime/index.js script.js
deno run -A runtime/index.js script.js
bun runtime/index.js script.js
```

Native binary compilation needs a C compiler: **Clang** (default, recommended), **GCC**, or **Zig**.

Optional parsers (`npm install -g porffor@latest --include=optional`): `@babel/parser` (TypeScript), `meriyah`, `hermes-parser`, `oxc-parser`.

```bash
porf script.js --parser=@babel/parser
porf script.js --parser=meriyah
porf script.js --parser=hermes-parser
```

## CLI

| Command | Purpose |
|---------|---------|
| `porf` / `porf run` | Compile and execute JavaScript |
| `porf wasm` | Compile to WebAssembly binary |
| `porf native` | Compile to native executables |
| `porf c` | Compile to C source |
| `porf lambda` | Compile to AWS Lambda packages |
| `porf profile` | Function-by-function performance analysis |
| `porf debug` | Interactive debugger |
| REPL | Interactive Read-Eval-Print Loop |

Examples:

```bash
porf hello.js -o hello
porf wasm script.js output.wasm
porf wasm -O3 script.js output.wasm
porf wasm --parse-types --opt-types script.ts output.wasm
porf native script.js output
porf native script.js output --compiler=clang   # or gcc / zig
porf native script.js output --cO=Ofast
porf c script.js output.c
```

Porffor does not currently use a standard import format like WASI, so generated Wasm binaries require Porffor's runtime imports for I/O.

### Optimization Levels

- `-O0`: No optimizations, fastest compilation, larger output
- `-O1`: Basic optimizations (default): instruction simplification, import tree-shaking
- `-O2`: Advanced optimizations (partial evaluation). Experimental and unstable
- `-O3`: Maximum optimizations

TypeScript: `--parse-types` to parse type annotations; `--opt-types` to use them as compiler hints. Porffor does **not** type-check; types are optimization hints only. If `--parse-types` is used without a parser, it switches to `@babel/parser`.

Valtype: default `--valtype=f64`; experimental `--valtype=i32`.

## TypeScript Support

```bash
porf --parse-types script.ts
porf --parse-types --opt-types script.ts
```

## AOT vs other engines

| Feature | Porffor (AOT) | V8/SpiderMonkey (JIT) | QuickJS (Interpreter) |
|---------|---------------|------------------------|------------------------|
| Startup time | Instant | Slower (warmup) | Instant |
| Peak performance | Good | Excellent | Poor |
| Binary size | Tiny | Large | Medium |
| Memory usage | Low | High | Medium |
| Dynamic eval | ❌ | ✅ | ✅ |
| Predictability | High | Low | High |

For the features it supports, Porffor is typically blazingly fast compared to interpreters and engines running without JIT. With compiler optimizations, typed input, and native compilation, it can compete with JIT-enabled engines.

Typical performance relative to Node.js (docs, workload-dependent):

- Wasm (interpreted): 2–5x faster
- Wasm (JIT): similar after warmup
- Native (2c + Ofast): 3–10x faster

Hello-world Wasm can be ~200 bytes. Official hello native binary example: 33.7KB compiled in ~105ms.

## Current Limitations

- **Limited async support** — `Promise` and `await` have known bugs
- **No cross-scope variables** — Variables cannot be accessed between scopes (except arguments and globals)
- **No dynamic evaluation** — `eval()` and `Function()` are not supported due to AOT compilation
- **Incomplete API coverage** — Many JavaScript APIs are not yet implemented
- Alpha / research project; not yet intended for serious use
- Native binaries via 2c are experimental, not sandboxed, and have not been proven fully safe

```javascript
// ❌ Not supported
eval('console.log("hello")');
Function('return 42')();

// ✅ Use direct code
console.log("hello");
const fn = () => 42;
```

## Type System (docs)

Each value is a pair `(value, type)` where type is an i32 identifier (`compiler/types.js`):

```javascript
export const TYPES = {
  undefined: 0x00,
  number: 0x01,
  boolean: 0x02,
  string: 0x03 | TYPE_FLAGS.length,
  bigint: 0x04,
  symbol: 0x05,
  function: 0x06,
  object: 0x07
};
```

Internal types:

- **ByteString** — 1 byte/char for ASCII/LATIN-1 (vs UTF-16 String at 2 bytes/char). Halves memory for ASCII strings. Many builtins must be written twice (String + ByteString).
- **i32** — primarily for pointers (Wasm i32 valtype; signedness is instruction-dependent)
- **f64** — default numeric valtype (IEEE 754 double)
- **i64** — 64-bit integer / bigint operations

Type flags:

```javascript
export const TYPE_FLAGS = {
  parity:    0b10000000,  // ByteString vs String
  length:    0b01000000,  // Has .length property
};
```

When writing Porffor builtins, explicit type annotations are required: `let a: number = 1;` not `let a = 1;`.

## 2c: WebAssembly to C Compiler

2c ("to C") is Porffor's own Wasm→C compiler (`compiler/2c.js`). It uses Porffor's internal information to generate specific, efficient C with minimal boilerplate — not like wasm2c.

```
JavaScript → Porffor Compiler → WebAssembly Bytecode
                                       ↓
                                   2c Compiler
                                       ↓
                                    C Source
                                       ↓
                                C Compiler (clang/gcc/zig)
                                       ↓
                                 Native Binary
```

Benefits: native performance, no runtime, standalone binary, cross-platform C, small footprint.

Tradeoffs: not sandboxed, experimental, larger than pure Wasm, longer compile time.

C compiler optimization (`--cO`): Ofast (default), O3, O2, O1, O0. Binaries are stripped by default.

`--2cMemcpy` uses memcpy instead of pointer casts (safer, possibly slower; helps alignment).

Functions typically return `(value, type)` pairs via `struct ReturnValue { f64 value; i32 type; }`.

Linear memory: `calloc` of `_memoryPages * 65536` (64KB pages).

Native binaries are **NOT sandboxed** — full filesystem, network, syscall, memory access. Do not compile untrusted code to native. Use Wasm if you need sandboxing.

Cross-compilation example via Zig:

```bash
porf c script.js output.c
zig cc -target x86_64-linux -O3 output.c -o output-linux
zig cc -target x86_64-windows -O3 output.c -o output.exe
zig cc -target aarch64-linux -O3 output.c -o output-arm
```

## WebAssembly Proposals Used

Only widely-implemented proposals:

- **Multi-value** (required)
- **Non-trapping float-to-int conversions** (required)
- **Bulk memory operations** (optional)
- **Exception handling** (optional, only for errors)
- **Tail calls** (opt-in, disabled by default)

## Use Cases / Design Notes

- Safety: written in JS (memory-safe) and compiles JS to Wasm (sandboxed). These rely on the underlying implementations being secure.
- Compile JS to native binaries (still very early)
- Inline Wasm (`Porffor.wasm` template tag) for beating the compiler or fine-grained functionality
- Potential for SIMD and other lower-level concepts
- Also: `porf profile`, `porf debug`, custom builtins, memory/pointer APIs
