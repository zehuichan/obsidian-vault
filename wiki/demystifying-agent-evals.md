# Demystifying Evals for AI Agents

Agent 评估（eval）的系统方法：用 task、trial、grader、transcript、outcome 这套术语定义评估，组合代码、模型、人工三类 grader，按 Agent 类型选方法，并按「从 0 到 1」路线图尽早起步，持续读 transcript 维护（Mikaela Grace 等, Anthropic, 2026-01-09）。

## 核心概念

- **术语**
  - task（problem / test case）：带输入和成功标准的单个测试
  - trial：对 task 的每次尝试；输出有随机性，需多次试验才稳定
  - grader：给 Agent 表现某一方面打分的逻辑；一个 task 可有多个 grader，每个含多条 assertion
  - transcript（trace / trajectory）：一次 trial 的完整记录，含输出、工具调用、推理和中间结果
  - outcome：trial 结束时环境的最终状态。订票 Agent 说「已订好」，但 outcome 是数据库里是否真有这条预订
  - evaluation harness：端到端运行评估的基础设施，提供指令和工具、并发运行、记录步骤、评分、汇总
  - agent harness（scaffold）：让模型成为 Agent 的系统；评估「一个 Agent」其实是评估 harness 与模型一起
  - evaluation suite：为衡量特定能力或行为而设计的一组任务
- **Agent 评估难在**：多轮、会修改环境状态，错误会传播和累积；前沿模型还会找到超出静态评估预期的方案。例：Opus 4.5 在 τ2-bench 订机票任务里发现政策漏洞，按评估原文是「失败」，其实给用户的方案更好
- **价值**：没有评估时调试是被动的（等投诉、手动复现、修复并祈祷没回归）；有了评估，换新模型能在数天内完成测试和升级，而不是数周，并且免费获得延迟、token、单任务成本、错误率的基线

## 为什么要建评估

- 早期靠手动测试、内部试用和直觉能走得很远；拐点往往是用户反映「改完更差了」，团队开始「盲飞」
- Claude Code 的路径：先靠内部员工和外部用户反馈快速迭代，后来先给简洁性、文件编辑等窄领域加评估，再扩到「过度工程」等复杂行为，并与生产监控、A/B 测试、用户研究等结合
- Descript：围绕「别搞坏东西、按我说的做、做得好」三个维度建评估，从手动评分演进到产品团队定义标准的 LLM grader 加定期人工校准，常设质量基准和回归测试两套
- Bolt：先有广泛使用的 Agent，3 个月内建起评估系统：静态分析评分、浏览器 Agent 测应用、LLM 评审判断指令遵循等行为
- 评估越早越好：产品需求自然转化成测试用例；晚了就是在对线上系统反推成功标准。评估还能消除歧义：两个工程师读同一份初始 spec，对边界情况可能理解不同

## Grader 三类

| 类型 | 方法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 代码型 | 字符串匹配、二元测试（fail-to-pass / pass-to-pass）、静态分析、结果验证、工具调用验证、transcript 分析 | 快、便宜、客观、可复现、易调试 | 对合理变体脆弱、缺乏细腻度、难评主观任务 |
| 模型型 | rubric 打分、自然语言断言、成对比较、参考式评估、多评审共识 | 灵活、可扩展、能抓细节、适合开放输出 | 非确定性、更贵、需要与人工校准 |
| 人工型 | 专家评审、众包、抽样检查、A/B 测试、标注者一致性 | 黄金标准、贴近专家用户判断、可校准模型 grader | 贵、慢、需要大规模专家 |

任务评分可加权（总分过阈值）、二元（所有 grader 都要过），或混合。

**能力评估 vs 回归评估**
- 能力评估问「这个 Agent 能做好什么」，应从低通过率起步，给团队一座可攀的山
- 回归评估问「以前能做的现在还能做吗」，应接近 100%；分数下降意味着出了问题
- 上线并优化后，通过率高的能力评估可「毕业」成为持续运行的回归套件

## 按 Agent 类型评估

**编码 Agent**
- 确定性 grader 天然合适：代码能跑吗、测试过了吗。SWE-bench Verified 给 GitHub issue、用测试套件评分，一年内 LLM 从 40% 涨到 80% 以上；Terminal-Bench 测端到端技术任务，如从源码构建 Linux 内核或训练 ML 模型
- 在二元验证之外，也可评 transcript：启发式代码质量规则、带清晰 rubric 的模型 grader 评估工具调用和与用户的交互
- 实践中通常以单元测试验证正确性、LLM rubric 评整体代码质量，按需增加其他 grader 和指标（轮数、工具调用数、总 token、首 token 延迟、输出速度等）

**对话 Agent**
- 交互质量本身就是评估的一部分；通常依赖可验证的最终状态和同时覆盖任务完成与交互质量的 rubric，常需第二个 LLM 模拟用户
- 成功是多维度的：工单是否解决（状态检查）、是否在 10 轮内（transcript 约束）、语气是否合适（LLM rubric）；τ-Bench 与 τ2-Bench 以此模拟零售支持、订机票等多轮交互
- 许多任务（如回答问题）有多个「正确」解，所以通常用模型型 grader 评沟通质量与目标完成

**研究 Agent**
- 质量只能相对任务判断；专家可能对「全面」有分歧，真相随参考内容变化，输出越长越开放越容易出错；BrowseComp 测的是在开放网络里「大海捞针」
- 组合 grader：groundedness 检查（断言有检索来源支持）、coverage 检查（好答案必须包含的关键事实）、来源质量检查（来源权威而非仅仅是首个检索结果）；有客观答案的任务用精确匹配
- LLM rubric 要频繁对照专家人工判断校准

**Computer use Agent**
- 通过截图、鼠标、键盘与 GUI 交互；需在真实或沙箱环境里运行并检查是否达成预期结果。WebArena 用 URL 与页面状态检查加后端状态验证（订单真下了，而不是只看到确认页）；OSWorld 扩展到整个操作系统，评估脚本检查文件系统、应用配置、数据库内容、UI 元素属性
- 浏览器使用要在 token 效率与延迟之间平衡：基于 DOM 的交互快但耗 token，基于截图的慢但更省 token；总结维基百科适合抽 DOM 文本，在亚马逊找笔记本包适合截图。Claude for Chrome 的评估就检查是否按场景选对工具

## 非确定性：pass@k 与 pass^k

- **pass@k**：k 次尝试中至少有一次正确的概率；k 越大越高。编码常看 pass@1；若只要有一个方案能用，也可看大 k
- **pass^k**：k 次尝试全部成功的概率；k 越大越低。若单次成功率 75%，3 次全过的概率为 0.75³ ≈ 42%；对面向客户、需要每次都可靠的 Agent 很重要
- k=1 时两者相同；k=10 时 pass@k 趋近 100%，pass^k 趋近 0%，讲的是相反的故事。按产品需求选：只要一次成功用 pass@k，要一致性用 pass^k

## 从 0 到 1 的路线图

**收集任务**
- **Step 0 尽早开始**：20–50 个来自真实失败的简单任务就是很好的开端；早期每次改动效应大，小样本就够；越晚越难
- **Step 1 从已有的手动检查起步**：开发中和每次发布前手动验证的行为、最终用户常做的任务；已上线则看 bug 跟踪和支持队列，按用户影响排优先级
- **Step 2 写无歧义的任务并配参考解**：好任务是两位领域专家独立得出同样的通过/失败结论；grader 检查的一切都应在任务描述里可见。审计 Terminal-Bench 发现：任务要求写脚本却没指定路径，而测试假设了特定路径，Agent 会无辜失败。前沿模型在大量试验后仍是 0%（pass@100 为 0），多半是任务坏了而不是 Agent 不行；参考解可证明任务可解且 grader 配置正确
- **Step 3 构建平衡的问题集**：既测应该发生的情形，也测不应发生的；单边评估导致单边优化。例：Claude.ai 的网络搜索评估，既要有「该搜」的查询（天气），也要有「该直接答」的（谁创立了苹果）；欠触发与过触发的平衡花了多轮迭代

**设计评估 harness 与 grader**
- **Step 4 稳定环境的健壮 harness**：评估里的 Agent 要与生产大体一致，环境本身不引入噪声；每个 trial 从干净环境开始。共享状态会造成关联失败，或虚高性能：内部评估中曾发现 Claude 通过查看之前 trial 的 git 历史占了便宜
- **Step 5 谨慎设计 grader**：能确定性就确定性，必要或要灵活时用 LLM，审慎使用人工验证
  - 不要检查固定的工具调用顺序，过于脆弱，因为 Agent 常找到设计者没预料到的有效路径；**评产出，不评路径**
  - 多部分任务设置部分得分：认出问题、验证客户但没退款，比一开始就失败强得多
  - LLM-as-judge 要与人类专家紧密校准；给它「Unknown」的出口以避免幻觉；为每个维度写清晰、结构化 rubric，并用独立的 LLM 评审逐维度打分，而不是一个评审评全部
  - 评估本身可能有隐蔽缺陷：Opus 4.5 在 CORE-Bench 上最初得 42%，一位研究员发现多个问题（评分死板，期望 96.124991… 时把 96.12 判错、任务规格含糊、随机任务无法精确复现），修复并换更宽松脚手架后升到 95%；METR 发现其时间视野基准中有任务配置错误，要求优化到设定的分数阈值，但评分却要求超过该阈值，惩罚了遵循指示的 Claude
  - 让 grader 不易被绕过或作弊：通过必须真的解决问题

**长期维护**
- **Step 6 读 transcript**：不读就不知道 grader 好不好。任务失败时，transcript 能告诉你是 Agent 真犯错还是 grader 拒绝了有效解；失败应「看着公平」
- **Step 7 监控能力评估饱和**：100% 只能追踪回归，不再提供改进信号。SWE-Bench Verified 今年从 30% 起步，前沿模型接近 80% 以上，趋于饱和；接近饱和时，大幅能力提升只体现为分数的小幅上涨。例：代码评审创业公司 Qodo 起初对 Opus 4.5 不惊艳，因为他们的一次性编码评估没抓到长任务上的提升，后来建了新的 agentic 评估框架。原则：没人深挖细节并读过 transcript 前，不要全信评估分数
- **Step 8 通过开放贡献保持评估套件健康**：评估是需要持续关注和明确所有权的活制品。Anthropic 最有效的是：专职评估团队拥有核心基础设施，领域专家和产品团队贡献大多数任务并自己运行评估；定义评估任务是检验产品需求是否具体到可以开工的最佳方式之一
  - 提倡**评估驱动开发**：在 Agent 能做到之前先建评估定义规划中的能力，再迭代到表现良好；从低通过率起步的能力评估，让「赌模型几个月后能做到」的功能一目了然，新模型发布时跑一遍套件就知道赌中了哪些
  - 产品经理、客户成功经理甚至销售，都可以用 Claude Code 以 PR 形式贡献评估任务，应当鼓励

## 评估并非全部：全面理解 Agent 表现

| 方法 | 优点 | 缺点 |
| --- | --- | --- |
| 自动化评估 | 迭代快、完全可复现、无用户影响、可每次提交运行 | 需前期投入、需持续维护防漂移、与真实使用不符会造成虚假信心 |
| 生产监控 | 反映真实用户行为、抓到合成评估漏掉的问题 | 被动，问题先触达用户；信号噪声大；缺乏评分基准 |
| A/B 测试 | 衡量真实用户结果（留存、任务完成） | 慢，需足够流量，只测已部署的改动，对「为什么」信号弱 |
| 用户反馈 | 暴露未预料的问题，带真实样例 | 稀疏、自选择、偏向严重问题，用户很少解释原因 |
| 手动 transcript 评审 | 建立对失败模式的直觉，抓到细微质量问题 | 耗时、不可扩展、覆盖不一致 |
| 系统性人工研究 | 多评审的金标准判断，适合主观任务，能校准模型 grader | 贵、周期长、难频繁运行 |

对应阶段：自动评估用于上线前和 CI/CD，是第一道防线；生产监控用于上线后检测分布漂移；A/B 测试在流量足够时验证重大改动；用户反馈和 transcript 评审持续进行（经常分流反馈、每周抽样读 transcript）；系统性人工研究用于校准 LLM grader 或评估主观输出。像安全工程里的瑞士奶酪模型，没有哪一层能抓住所有问题。

## 评估框架

- **Harbor**：在容器化环境里运行 Agent，支持跨云规模化运行 trial，任务与 grader 格式标准化；Terminal-Bench 2.0 等通过其 registry 发布
- **Braintrust**：离线评估加生产可观测与实验追踪，`autoevals` 库含事实性、相关性等预置 scorer
- **LangSmith**：追踪、离线与在线评估、数据集管理，与 LangChain 生态紧密集成；**Langfuse** 是自托管开源替代
- **Arize**：开源 Phoenix（LLM 追踪、调试、评估）与 SaaS 的 AX
- 框架只在你放入的评估任务质量范围内有价值：快速选一个适合工作流的，然后把精力花在高质量测试用例和 grader 上
