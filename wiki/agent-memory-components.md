# The Components of Agent Memory

Agent 记忆是 Claude 从经验中获得、跨会话保留、保存为日后可读上下文的知识；「dreaming」（离线回看日志来纠错、写新笔记、建新表示、调整预载内容）是让这份记忆保持准确且可检索的关键手段（Lance Martin, Anthropic, 2026-11-06）。

## 核心概念

- **记忆的范围**：只指保存成上下文、供之后读取的经验知识；不包括权重变化、会话内的 in-context learning、也不包括 compaction（用摘要替换旧轮次）
- **Dreaming**：类比人脑在睡眠或静息时回放并巩固经历。Letta 与 UC Berkeley 的研究者提出 sleep-time compute，让模型利用交互之间的空闲时间重组已有上下文；同一思路可让 Agent 回看日志，修正错误或产出新笔记和表示
- **记忆有时是一种预测**：写下规则，等于预测该模式将再次相关；写下已验证的事实，等于预测未来的 Agent 会想直接依赖它而不必复查
- **记忆表示**：笔记文件夹、wiki（Claude 自己写并维护、互相链接的页面）、层级结构（顶层预载，下层按需读或搜索）
- **分工**：会话内写笔记是「当场」判断显著性，但会分散主任务注意力；dreaming 把记忆生成推到后台，但产出不一定立刻可用

## 学习闭环：CL-Bench 1.0

任务：Claude 查数据库回答一系列问题，每次答完拿到正确答案，可写记忆；每题新会话，唯一持续的是一个记忆目录（用 Claude Managed Agents 运行）。

- Sonnet 4.6：能提出答错原因的理论，但记忆目录里是零散文件，各列几个未验证的猜测
- Opus 4.7：把笔记合并成单一参考文档，并开始标注哪些事实已核对、哪些未确认
- Sonnet 5：评分器核对后把答案标为已确认，答错时写更正
- Opus 5：首个**闭环**的模型，条目里包含规则、如何知道规则为真、之前问题的答案以及发现的陷阱
- Opus 5.5 与 Sonnet 5.5 同样闭环；有记忆时得分与 Opus 5 相近，但无记忆基线略高

## 显著性判断：Pokémon Red

对比约 10,000 步时的记忆目录：

- Sonnet 3.7：什么都可能重要，每场战斗、每件道具、每个 NPC 一个文件，最终 **413 个文件、225 个文件夹**，只拿 1 个徽章；游戏状态不断变化，旧记录持续过期，后来花更多精力翻记忆而不是玩（第 4 套「master」记忆文件，随后 17 步创建 6 个文件、删 9 个、游戏内无动作）
- Fable 5：**9 个文件、2 个文件夹**，外加一个 `global.md`，拿到 4 个徽章。只记游戏不会告诉它的东西（策略、计划、验证过的规则），不记屏幕上每回合可读的信息（金钱、位置）；`global.md` 像仪表盘，含当前目标、道馆攻略计划和自己的记忆使用规则，`locations/` 放路线，`gameplay/` 放策略，例如连续 7 个精灵球失败后记下「连续 3+ 球失败就改变时机」
- Opus 5.5 类似：小文件夹记目标与下一步，边玩边重写，通关

## 如何引导 Claude 写记忆

- **告诉它记忆是干什么的，不告诉它怎么用**：CL-Bench 上只说有个记忆文件夹，对 Opus 4.7 和 Opus 5 就足够并带来明显提升
- 给具体规则反而可能有害：规则设为「只记录失败」时，Opus 5 与 Opus 4.7 失去了记忆带来的大部分收益；对更强模型，让它自己判断显著性更好
- 引导对老模型帮助最大：Sonnet 4.6 常不读记忆、不检验理论；提示它先读记忆再回答并显式检验理论，基准分数几乎翻倍。Sonnet 5 自己就会：答题前读记忆 10 次里有 9 次，Sonnet 4.6 不到一半
- 对前沿模型，通常只给简单指引：用户要求或明显值得记时就写，其余交给 Claude 判断

## Dreaming 的五种用途

**1. 纠正记忆**
- 会话内写下的笔记可能一开始就错，或随环境漂移，而之后会被信任
- 例：Claude 误记 PokéCenter 在山的东侧，走出来就宣布「Mt Moon 在身后」并记下「Mt Moon DONE」，随后掉下单向悬崖回到来路，却结论是「我走过头了」；用 dreaming 对照会话转录（ground truth）校验后，重写笔记，Claude 回洞穴并最终到达 Cerulean City；未纠正的那次三次回到旧路径，最后一路走回 Pewter City，始终没到 Cerulean

**2. 构建新的记忆表示（wiki）**
- 用 Stainless 的内部文档（约 350,000 个文件、约 4.2 亿 token）和 25 道问题测试；让 Opus 5 Agent 在 128 个会话里探索文件、写或改带链接的 wiki 页面、合并重复、对照源文件核对，用共享日志协调；从 2 个会话扩到 128 个，25 题的得分从 13% 涨到 48%（按评分标准项）
- wiki 配合搜索工具最有效：同时用搜索和 wiki 时总分随 wiki 增长从 54% 升到 61%，只用搜索是 53%，只用 wiki 最好 48%；同时每题省约 20,000 token
- 合并交易文档的 24 题测试中，跨文档综合类题目（占一半以上，很多还需判断或计算）用 wiki 得 87%，只搜索得 73%
- 并非总有用：在 LAB 的某个任务里，答案能从单个文档文本搜索得到，wiki 没明显收益；另一任务里 wiki 比原文还大，像博尔赫斯笔下与帝国一样大的地图，抽象了个寂寞

**3. 把笔记提升到记忆层级的顶层**
- 顶层由 harness 在每个会话开头预载，Claude 无需搜索，甚至不必知道有东西可搜
- 但要谨慎：预载占用 token，错误笔记会带进每个会话；加载也不保证 Claude 照做，Claude Code 文档指出更长的指令文件会降低遵循度。所以顶层必须小，dreaming 很大一部分工作就是把细节下沉并留链接
- Claude Code 的 auto memory 同理：只加载 `MEMORY.md` 的前 200 行或 25 KB，这段头部像索引，告诉 Claude 知道什么、去哪找

**4. 让记忆服务于特定目标**
- 例：LAB 里模拟公司收购的任务，按合同条款评分。最初的 wiki 生成指令没强调条款，多个 Agent 同时写同一张共享表，互相覆盖，57 个事实只保留 41 个（72%）
- 让 Claude 反思失败、提出改指令、重建 wiki 的循环后，指令改成：每份合同一页，由单个 Agent 写，逐字引用条款而不是汇总进共享表；结果 57/57，100%

**5. 补全会话留下的空缺**
- 写笔记时 Claude 只看得到当前会话；dreaming 可跨多个会话找共性模式或共同错误
- 例：wiki 常链接到尚未创建的页面，第二轮 dreaming 把 9 个指向缺页的链接重定向到同一文档已有的页面，并新增 3 个页面，包括一个索引

## 开放问题

- **何时创建记忆**：当场写能在源头抓住显著性，但分散注意力；dreaming 放后台，但产出不一定立刻可得
- **如何保持更新**：错误预测、一开始就错的规则、环境漂移；dreaming 能修正但耗算力，不可能持续检查所有记忆，可聚焦易变信息或按访问频率调节节奏
- **转录搜索作为基础**：把表示（如 wiki）与搜索结合有时有效，但维护表示需要算力，且要防止累积错误或幻觉
- 没有模型能真正知道未来会发生什么；dreaming 提供回看、整理、纠错和维护表示的机会
